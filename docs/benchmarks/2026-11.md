# Import and precompute benchmark, November 2026

This benchmark imports four public event logs from 4TU.ResearchData into a local `make up` stack. Each log is imported once, through the normal import endpoint, and then every bundled module that has a precompute step is timed on it.

- Raw results: [`2026-11.json`](./2026-11.json)
- Harness: [`scripts/benchmark/`](../../scripts/benchmark/)
- Run: 2026-11-10, 20:08 to 20:32 UTC, harness at commit `5069a61`. Since then the harness only starts its memory stream earlier and the renderer prints `n/a` for an import with no memory reading; neither changes any job timing. The application code is unchanged from `main` (`860d360`).

- **Import** is the `event_log.import` job's `finished_at - started_at`, read from the `jobs` table. It covers the steps from parsing to Parquet to a `ready` log. Uploading the file to the staging endpoint happens before the job, so it is not included.
- **Import queue wait** is `started_at - created_at` for the same job.
- **Peak api mem**:
  - It is the highest `docker stats` MemUsage of the `mate-api` container among samples taken inside the import job's own `started_at`–`finished_at` window.
  - The `docker stats` stream prints a line every 0.5 s, but each reading refreshes only about once a second. Window boundaries are therefore accurate to about 1 s.
  - MemUsage is the container's cgroup figure, which on cgroup v1 can include active page cache.
  - The idle container measured 385 MiB (median of 10 s sampled before the first import).
  - \*No `docker stats` reading arrived before the 0.72 s Sepsis import job ended: the stream's first line takes about 0.5 to 1 s. The first reading after it (400 MiB) was taken once the import had finished, possibly after eager `discovery` had started, so it is not reported. Per-module peaks in the JSON with `mem_samples: 0` have the same caveat. The harness now starts the stream 1.5 s before each job; this run predates that change.
- **Precompute min, median and max** are over the 8 modules whose job completed. `cv4cdd` is excluded (see below).

Which modules are covered:
- **The 9 timed modules** are the bundled modules with a job-backed `log.imported` handler. Eight use `@on_event` with `@job` in Python. `performance_java` uses `onEventJob` in the JVM SDK. The other 9 bundled modules compute only on request, so there is nothing to time here.
- **`cv4cdd` fails in a stock stack**, after about 2 s, with `RuntimeError: No CV4CDD detection model is available`. An administrator has to pin or upload its detection model, and this run did neither.
- **`discovery`** is the only module with `precompute: eager`, so each import started it. The harness requested every other module through `POST /event-logs/{id}/module-runs/{module}`.
- **Memory during `discovery`.** The api container peaked at 6.4 GiB on BPI 2019 and 4.2 GiB on BPI 2017 while `discovery` ran. These are whole-container figures and include memory still held from earlier jobs. Per-module peaks are in the JSON.

**Repeatability.** A first run 30 minutes earlier, on a stack reset the same way, gave every import and `discovery` time within 5% of these. The exception is the sub-second Sepsis import: 0.68 s vs 0.72 s, a 6% difference. That first run's memory capture also took in the start of eager `discovery`, which is why the harness was changed and the benchmark re-run.

## Method

1. Download the logs and check their MD5 sums:

   ```bash
   sh scripts/benchmark/fetch_logs.sh bench-logs
   ```

2. Start the stack from empty:
   - Run `cp .env.example .env`. The harness logs in with the demo token, so it needs `DEMO_MODE=true`.
   - Run `docker compose down -v`, remove `data/users` and `data/staging`, then run `make up`.
   - Module venvs from an earlier boot were reused, so the first boot was not timed.

3. Run the harness. It does the following:
   - It calls `POST /modules/restore-defaults`, which gives the demo account the bundled default modules, the same set a new account gets. It then samples idle memory for 10 s.
   - It handles the logs one at a time, in command-line order (here smallest first), with no other load on the stack. For each log it:
     - stages the file (`POST /event-logs/stage`) and imports it (`POST /event-logs`),
     - samples `docker stats` while the import runs,
     - waits for eager `discovery`, then requests each remaining module one at a time,
     - reads every job's timestamps from the `jobs` table.
   - It cancels any module run still going after 30 minutes. None came close to that.

   ```bash
   uv run python scripts/benchmark/import_benchmark.py \
     --log sepsis=bench-logs/sepsis.xes.gz \
     --log road_traffic=bench-logs/road_traffic.xes.gz \
     --log bpic2017=bench-logs/bpic2017.xes.gz \
     --log bpic2019=bench-logs/bpic2019.xes \
     --roles 'sepsis={"resource": "org:group"}' \
     --roles 'bpic2017={"activity": "activity"}' \
     --roles 'bpic2019={"resource": "resource"}' \
     --module-timeout 1800 -o bench.json
   ```

4. Render the tables. The tables in this doc are this script's output; only the `*` footnote marker was added by hand. The renderer prints `n/a` for an import with no memory reading inside the job window.

   ```bash
   uv run python scripts/benchmark/render_benchmark.py bench.json
   ```

### Column roles

The automatic role resolver picks the wrong column for three of the four logs. The harness therefore pins roles, the same way the import wizard's role picker does. The wrong mappings below are what the stage endpoint proposed for each file.

| Log | Auto-resolved (wrong) | Pinned |
|---|---|---|
| Sepsis | `resource` → `Age` | `resource` → `org:group` |
| BPI 2017 | `activity` → `Action` (5 values instead of the 26 activities) | `activity` → `activity` (`concept:name`) |
| BPI 2019 | `resource` → `User`; `end_timestamp` → `Spend area text` | `resource` → `resource` (`org:resource`) |

- **Cause:** `_find_column` in `apps/api/src/mate/api/ingest/mapping.py`. It walks the columns in file order before it considers alias priority, and its fuzzy pass matches substrings in both directions:
  - `Action` is an `activity` alias and comes before `activity` in BPI 2017's columns.
  - `"age"` is a substring of the `resource` alias `"agent"`.
  - `"end"` is a substring of `"spend area text"`.
- **What a pin cannot fix.** A pin cannot unset a role. BPI 2019 is still imported with `end_timestamp` → `Spend area text`. The stored `events.parquet` has `end_timestamp` null on all 1,595,923 events, and the `Spend area text` column is gone. Any module that reads end timestamps sees none on BPI 2019.
- **Effect on timings.**
  - With the wrong `activity` mapping, BPI 2017's `discovery` took 121 to 151 s in the earlier investigation runs, against 6.6 min here.
  - That comparison is not controlled: those runs used other setups, some in-process with SQLite.
  - The direction is still clear. Without pinning, the numbers would understate BPI 2017's cost.
- **Status.** This benchmark does not change the resolver.

### Environment shim (sandbox only)

The machine that ran this benchmark sends outbound HTTPS through a TLS-intercepting proxy. The base images therefore had to trust the proxy's CA.

- **Rebuilt base images.** Both were rebuilt locally from pinned digests:
  - `python:3.12-slim@sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b`, with the CA added. It sets `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `UV_NATIVE_TLS=1` and an apt `CAInfo` entry.
  - `node:22.18.0-alpine@sha256:1b2479dd35a99687d6638f5976fd235e26c5b37e8122f786fcd5fe231d63de5b`, with `NODE_EXTRA_CA_CERTS`.
- **How they were wired in.** An untracked compose override fed them to the build through `build.additional_contexts`. It also set `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` on the api container.
- **Scope.** These settings only affect how dependencies download. No tracked compose files or Dockerfiles were changed. On a normal network, use plain `make up`.

## Sepsis: slow imports on the hosted instance

Two Sepsis imports on the hosted instance were reported at 28 and 37 minutes, against about a minute for BPI 2017. This gap did not reproduce, and no code fix was made.

- **In this run:**
  - The Sepsis import job took 0.7 s and BPI 2017's took 48.1 s.
  - The 8 completed precompute steps for Sepsis took 39 s in total.
- **Earlier investigation.** Four separate investigations profiled each import stage on Sepsis. They mostly ran in-process against SQLite, with one run on a `make up` stack, at an earlier commit and with auto-resolved roles. They covered:
  - XES parsing,
  - timestamp coercion with mixed `+01:00`/`+02:00` offsets,
  - sparse attribute coercion,
  - the Parquet write,
  - case and variant aggregation,
  - eager `discovery`,
  - the server-side CP-SAT DFG layout.

  Every import stage took under a second. `discovery` took 24 to 33 s. The DFG layout, which only runs when the panel asks for a server layout and not as part of import, took 3 to 7 s. No stage got slower out of proportion because of Sepsis's sparse attributes or mixed time-zone offsets.
- **What "import" meant on the hosted instance is unknown.** If it means job wall time, as in the Import column above, BPI 2017's "about a minute" matches this run. But a 28-to-37-minute Sepsis job would then contradict every local measurement. The explanation below holds only if the hosted figure was measured from upload to `ready`, which includes queue wait.
- **Most likely explanation: queue wait on a shared instance.** Not confirmed.
  - `JobRuntime` serves a single first-in, first-out queue with `worker_concurrency` workers (default 2; an admin setting can override it). The stored `priority` field is never used for ordering.
  - A new import waits until every job queued ahead of it has been picked up. While long module jobs from any user hold both workers, nothing gets picked up.
  - At this commit the runtime also stops any job still running after `job_execution_timeout_seconds` (default 1800 s). The comment on that setting cites "cross-user starvation we saw (one user's stuck precompute jobs draining the shared pool)". With that default, a completed 37-minute import cannot be 37 minutes of work inside the job. Whether the hosted instance ran with this setting is unknown.
  - Contention from an in-process module job running alongside the import could add seconds of in-job variance, but not tens of minutes.
- **How to confirm it.** The hosted `jobs` rows for the two imports would settle it. If `started_at - created_at` is about 30 minutes and `finished_at - started_at` is about a second, the time was queue wait. That is why this benchmark reports queue wait as its own column. In this run, with no other load, the longest queue wait for any job was 21 ms.
