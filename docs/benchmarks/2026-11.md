# Import and precompute benchmark, November 2026

This benchmark imports four public event logs from 4TU.ResearchData into a local `make up` stack. Each log is imported once, through the normal import endpoint. It then times every bundled module that has a precompute step.

- Raw results: [`2026-11.json`](./2026-11.json)
- Harness: [`scripts/benchmark/`](../../scripts/benchmark/)
- Run: 2026-11-10, 19:34 to 19:58 UTC, at commit `430f6d5`.

## Method

1. Bring the stack up from empty: `docker compose down -v`, remove `data/users` and `data/staging`, then `make up`. The module venvs from an earlier boot were reused, so the boot itself was not timed.
2. Run the harness. It does the following:
   - It calls `POST /modules/restore-defaults` to give the demo account the bundled defaults, the same set a new account gets.
   - It processes the logs one after another, smallest first, with no other load on the stack. For each log:
     - It stages the file (`POST /event-logs/stage`) and imports it (`POST /event-logs`).
     - It samples `docker stats` until the import job ends.
     - It waits for eager `discovery`, then requests each remaining module one at a time.
     - It reads all job timestamps from the `jobs` table.
   - Each module run has a 30-minute cap. No run came close to it.

   ```bash
   uv run python scripts/benchmark/import_benchmark.py \
     --log sepsis="Sepsis Cases - Event Log.xes.gz" \
     --log road_traffic=Road_Traffic_Fine_Management_Process.xes.gz \
     --log bpic2017="BPI Challenge 2017.xes.gz" \
     --log bpic2019=BPI_Challenge_2019.xes \
     --roles 'sepsis={"resource": "org:group"}' \
     --roles 'bpic2017={"activity": "activity"}' \
     --roles 'bpic2019={"resource": "resource"}' \
     --module-timeout 1800 -o bench.json
   ```

3. Render the tables:

   ```bash
   uv run python scripts/benchmark/render_benchmark.py bench.json
   ```

### Column roles

The automatic role resolver picks the wrong column on three of the four logs. Because of this, the harness pins roles the same way the import wizard's role picker does:

| Log | Auto-resolved (wrong) | Pinned |
|---|---|---|
| Sepsis | `resource` → `Age` | `resource` → `org:group` |
| BPI 2017 | `activity` → `Action` (5 values, not the 26 activities) | `activity` → `activity` (`concept:name`) |
| BPI 2019 | `resource` → `User`; `end_timestamp` → `Spend area text` | `resource` → `resource` (`org:resource`) |

- **Cause.** `_find_column` (`apps/api/src/mate/api/ingest/mapping.py`) loops over columns in file order before it looks at alias priority, and its fuzzy pass matches substrings in both directions:
  - `Action` is an `activity` alias and comes before `activity` in BPI 2017's columns.
  - `"age"` is a substring of the `resource` alias `"agent"`.
  - `"end"` is a substring of `"spend area text"`.
- **What pinning cannot fix.** A pin cannot unset a role. BPI 2019 therefore still gets `end_timestamp` → `Spend area text`, and that text column is coerced to an all-NaT `end_timestamp`. This affects any module that reads end timestamps on BPI 2019.
- **Effect on timings.** With the wrong `activity` mapping, BPI 2017's `discovery` took 134 to 151 s in the investigation runs, against 6.6 min here. Unpinned numbers would understate its cost.
- **Status.** The resolver itself is not changed in this benchmark.

### Environment shim (sandbox only)

The machine that ran this sends outbound HTTPS through a TLS-intercepting proxy. The `python:3.12-slim` and `node:22.18.0-alpine` base images were therefore rebuilt locally with the proxy's CA added. They are passed to the build through an untracked compose override (`build.additional_contexts`), with `SSL_CERT_FILE` set for the api container. Nothing else differs from `make up`: no tracked compose files or Dockerfiles were changed, and the shim does not touch anything on the measured path. On a normal network, run plain `make up`.

## Sepsis: slow imports on the hosted instance

On the hosted instance, two Sepsis imports were reported at 28 and 37 minutes, against about 1 minute for BPI 2017. That gap does not reproduce, and no code fix was made.

- **This run.** Sepsis imports in 0.7 s and BPI 2017 in 46.5 s, which matches the hosted figure of "about a minute". The 8 completed precompute steps for Sepsis take 39 s in total.
- **Separate investigation.** Four independent investigations profiled each import stage on Sepsis, in-process and on this compose stack. They looked at:
  - XES parse, timestamp coercion with mixed `+01:00`/`+02:00` offsets, and sparse attribute coercion.
  - Parquet write, case and variant aggregation.
  - Eager `discovery`, and the CP-SAT DFG layout.

  Every stage takes less than a second, except `discovery` at 24 to 33 s. Nothing in the code grows superlinearly on Sepsis-shaped input.
- **Most likely explanation (not confirmed): queue wait on a shared instance.** `JobRuntime` serves one FIFO queue with `WORKER_CONCURRENCY` workers (default 2). The stored `priority` is never used for ordering. While two long module jobs, from any user, hold both workers, a new import waits for one of them to finish. That wait would count toward "import time" if it was measured from upload to `ready`. It also explains why two identical uploads took different times (28 vs 37 min), which no code path inside the job can do.
- **Confirming it.** The hosted `jobs` rows for the two imports would settle it. If `started_at - created_at` is about 30 min and `finished_at - started_at` is about 1 s, the cause is queue wait. This benchmark reports queue wait as its own column so the problem would show up if it recurs. In this run the queue wait was 0.01 s or less for every job, because no other load was running.
